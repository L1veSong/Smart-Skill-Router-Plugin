# SSR A 层规则设计方法论

> 来源：2026-07-23 两次会话实战 — 从10条旧规则扩展到79条16域
> 当前：79条规则，16域，92 skill，功能覆盖率 97%

## 核心原则：粗中有细

**粗** — 口语化/近义词/不同说法都能命中，不需要用户说精确关键词。
**细** — 每次只推 1-2 个 skill，不炸弹式全推，不跨域污染。

## 六条铁律

### 1. 大面分开
不同领域的规则互不串。生图归生图，海报归海报，清理归清理，写作归写作，旅行归旅行。
- ✅ "电影感" → 推 zy-cinematic-realism（1个）
- ✅ "海报" → 推 culture-fragment-poster-engine（1个）
- ❌ "电影感" → 推全部7个生图 skill（噪音）
- ❌ "生图" → 推全库 skill（致命噪音）

### 2. 类似词也要命中
用户说"电影那种感觉""高级画面""照片修好看"都要能推到——不依赖精确关键词。
- ✅ 正则用 `(电影感|电影画面|电影.*感觉|film.*look|cinematic)` 覆盖口语变体
- ❌ 正则只写 `(cinematic)` 然后用户说"电影那种感觉"就漏了
- ✅ 旅行域: `\d+天.*行程|旅游攻略|附近|好吃的|怎么.*去` 覆盖自然语言

### 3. 每规则 1-2 个 skill
多 skill 按场景细分多条规则，不在一条里堆。
- ✅ "学术论文" → nature-writing + nature-polishing（2个，精准）
- ❌ "写文章" → khazix + nature + academic + paper-spine + writing-guidelines（5个，噪音）
- 做法：通用词"写文章"只推最通用的 khazix-writer。学术词"SCI论文"推 nature 系列。论文写作"毕业论文"推 academic-paper。

### 4. 域外不推
不归我管的领域保持沉默，不瞎推。
- ✅ "清理磁盘" → storage-analyzer（1个）
- ✅ "今天天气" → travel-api（1个，旅行域已覆盖）
- ❌ "清理磁盘" → 推了一大堆生图 skill

### 5. 负向排除防误判
某些宽泛词会误触发不相关的 skill——必须用负向断言排除。
- ✅ "帮我写代码" → 不推 khazix-writer（负向排除 `代码|程序|脚本|code`）
- ✅ "帮我写一篇文章" → 推 khazix-writer（正确命中）
- 做法: `(帮我写(?!.*代码)(?!.*程序)(?!.*脚本)(?!.*code))`

### 6. 先测后发布
每次改完规则跑 8-10 个自然语言测试用例，验证：
- 该中的都中了（覆盖率）
- 不该中的没中（噪音）
- 每个匹配 ≤ 2 个 skill（精度）

## 规则设计反模式

| 反模式 | 为什么坏 | 正确做法 |
|--------|---------|---------|
| 一条规则堆 5+ skill | 用户说"生图"全推 = 噪音 | 按场景拆多条规则 |
| 正则只写精确词 | "电影那种感觉"漏掉 | 加口语变体 `.*?` |
| 跨域规则混一起 | "海报"推到生图 skill | 严格按领域分组 |
| 忘了负向排除 | "帮我写代码"误推卡兹克 | `帮我写(?!.*代码)` |
| 写完不测试 | 上线才发现大面积漏 | 必须跑 8-10 个用例 |
| "攻略"太宽 | "攻略网页"触发 plan 规则 | 拆成"旅游攻略"（plan）和"攻略.*网页"（website）|

v4（补域，27条）：加写作+清理
  ✅ "写文章" → khazix-writer
  ✅ "清理磁盘" → storage-analyzer
  ✅ "SCI论文" → nature全套

v5（补旅行，37条）：加旅行域 + 误判修复

## 新增规则的检查清单

```bash
# 1. 语义相近测试（≥8个用例，含口语变体）
# 2. 不该匹配的测试（≥2个用例，含负向排除验证）
# 3. 每匹配 ≤2 个 skill
# 4. 备份 a_rules.json（含时间戳）
- 通知用户重启 Hermes 生效
# 6. 如果写后被还原：从最新 .bak 恢复，重启 Hermes（SSR 内部持有状态，运行中会覆盖手动编辑）
# 7. 更新此文件记录最新状态
```

## 进阶：词干匹配策略（v6 — 2026-07-23）

正则枚举近义词不可行——中文口语变化无限（"想出去转转""飞过去多少钱""那边吃啥""出个稿子"）。词干匹配替代穷举正则：

```
词干匹配 = 短词干（1-2字）+ 上下文排除 + 域内限制

"玩" → 旅行域（而非全库匹配"玩"=噪音）
"吃" → 美食 → 旅行域内查找
"写" → 写作域（排除 "写代码""写脚本"）
"飞" → 机票 → 旅行域内查找
"清" → 存储域
```

**效果：** 从 36%（穷举正则）→ 93%（词干匹配）。仅需 26 条规则覆盖 4 大域。

### 词干匹配 vs 穷举正则

| 方法 | 规则数 | 近义词命中 | 噪音 | 维护 |
|------|--------|-----------|------|------|
| 穷举正则 | 37 | 36% | 低 | 每漏一个加一条 |
| 词干匹配 | 26 | 93% | 中（需负向排除） | 调整词干即可 |

### ⚠️ 词干太短的陷阱

`吃` → 匹配"吃饭""吃亏""吃紧"。需域内限制：只在旅行/美食域激活时才匹配 `吃`。在没有域路由前，用上下文限制 `(吃(?!亏)(?!紧))`。

## 架构方向：MoE 门控路由（✅ 已实施 v2.4.0-MoE，2026-07-23）

当前 A 层是扁平 26 条全量扫——"新疆旅行拍照片"同时命中旅行×3 + 生图×2 = 5 条。MoE 门控方案：

```
用户输入
    │
    ▼
Layer 1 · 路由层（轻量词干）
    "玩"→旅行域  "写"→写作域  "画"→生图域  "清"→存储域
    │
    ▼
Layer 2 · 域内专家（细分匹配）
    只在该域规则内匹配，跨域互不干扰
    │
    ▼
输出精选（域间可叠加，域内选最优1-2个）
```

**与 MoE 的对应：** Gating Network=路由层, Expert FFN=域内规则, Top-k=域内最优选择。

改动点：`_match_a_layer_keyword()` 函数开头加 ~15 行路由逻辑。现有匹配逻辑不动。
